## Detail by theme

### AI capability gaps (highest product relevance)

**TD-01 — No autonomous production Classification/Metadata Extraction provider.** This is, in the pipeline's own words, repeated verbatim in two separate modules' `KNOWN_LIMITATIONS.md`, *"the single largest gap between 'feature complete' and 'fully autonomous.'"* Every judgment-dependent file (ambiguous documents, screenshots, anything Category-uncertain) currently requires a live, in-session Claude conversation to classify — `ClaudeLiveClassifier` has no unattended equivalent. Run without a live session, every judgment file falls back to `Category.UNKNOWN`, which in turn drives it toward `review_required` in Module 06's scoring. This single gap is the reason Scheduled mode, despite being marked "Supported" in `README.md`'s execution-modes table, has never actually been proven end-to-end: a scheduled run with no human present to make judgment calls would silently degrade into a pile of low-confidence, unreviewed files rather than the clean automation the mode implies.

**Update, 2026-07-23:** C1's Product Acceptance Test directly confirmed this gap in a fresh, concrete way (C1-PAT-2): `run`, invoked from a plain terminal with no live Claude session attached, cannot produce `auto` or `approval_required` outcomes for any judgment-dependent file. Scope and target unchanged — this is corroborating evidence, not a new finding.

**Update, 2026-07-26 (TD-01 v0.9 — partially resolved):** v0.9's Provider Registry, Claude API provider (`src/providers/claude.py`), config support, opt-in consent flow (`python -m src.cli provider enable/disable/status`), and Provider Evaluation Harness shipped — see `Build-out/02 Classification/TD-01 Provider Architecture — Design Package.md` §5–§7 and `Tests/Provider Evaluation Harness/TD-01 v0.9 Validation Report.md` for the full validation cycle. All five design-committed acceptance criteria met; full regression suite green (889/889). **Off by default** — `ai_provider_consent: false` ships as the safe default, so today's fallback behavior (`Category.UNKNOWN`/null fields outside a live session) is completely unchanged unless a user explicitly opts in. **Not yet validated with a real API key** — no `ANTHROPIC_API_KEY` was available in the implementation environment, so no live classification/extraction judgment call has actually been made by the new provider; only the unconfigured-provider fallback path and the harness's own mechanics (against a fake stub provider) were exercised end-to-end. This is why TD-01 is *partially*, not fully, resolved: the architecture and safety rails are proven; whether Claude's real output actually improves Unknown %/naming quality/confidence distribution the way §1's problem statement projects is still unverified. Target updated accordingly: first real-key validation run, then reassess for full closure.

**Update, 2026-07-26 (TD-01 — Implementation Complete, Production Quality Validation Deferred/External Dependency):** the real-key validation run referenced above was executed locally against the live Anthropic API path. Registry resolution, isolated storage, the full pipeline chain, cost estimation, and rollback (`provider disable`/`status` confirmed) all executed correctly — engineering scope is complete and verified. The run made zero successful billable API calls because no Anthropic API credits were available, so Q1–Q4 (real judgment quality vs. deterministic baseline) remain unanswered — this is an external billing dependency, not an engineering defect, and does not block beta since the feature is off by default. TD-01 status is closed for engineering purposes; the deferred judgment-quality validation is tracked as a future, separately-billed post-beta activity, not an open engineering item.

**TD-19 — Judgment quality validated on small, self-graded samples.** Modules 02 and 03 each validated their live-judgment path against a single UAT batch (8 and 9 judgment calls respectively), graded by the same person who built the feature. Both `KNOWN_LIMITATIONS.md` files say this plainly: *"should not be read as statistically meaningful validation... at scale."* This matters more once TD-01 is addressed — an automated provider needs a real accuracy baseline to be trusted, and one doesn't yet exist.

### Automation gaps

**TD-02 — The approval delivery mechanism was never decided.** Module 07's Open Decision OD-3 — *how* a human's `ApprovalDecision`s actually reach the system (an interactive chat table, a generated markup file the user edits, something else) — was explicitly left unresolved at freeze and never revisited. Core batch logic is deliberately indifferent to it, which was the right call for building the engine, but it means there is today no defined, repeatable interaction pattern for approval outside of an ad hoc Claude conversation. This is a prerequisite for both real automation (TD-01/TD-10) and any real user interface (see `PRODUCT_ROADMAP.md`).

**Update, 2026-07-23:** C1's interactive approval prompt (`_prompt_decision()`/`_collect_decisions_interactively()` in `src/cli.py`) is the first concrete resolution OD-3 has ever received — but only for the *attended* case, where a human is at the terminal. The *unattended* case is unchanged and remains exactly as open as before (C1-PAT-8b: non-interactive `execute` with closed stdin crashes rather than resolving decisions any other way). TD-02 is therefore marked **partially resolved**, not closed.

**TD-10/TD-11 — Watch Folder mode and multi-source support** are both architected for (the "Source" concept already generalizes) but not built. Both are explicitly Version 3 items in `ROADMAP.md`, deferred as "a bigger engineering lift... only worth building once daily/on-demand scans prove too slow in practice" — a condition that has not yet been tested, because the pipeline has never run against a real folder (see `PROJECT_RETROSPECTIVE.md` §3).

### Infrastructure / scale debt

TD-03 through TD-06 are all variations on the same accepted trade-off: JSON-file storage and linear scans are simple, auditable, and fast enough at v1's tested volumes (tens of files per batch), and every module that touches them re-discloses the cost per `Governance/ARCHITECTURE_DECISIONS.md` decision 11's explicit requirement. None of these are urgent. All of them become urgent at the same inflection point — real, sustained daily use accumulating hundreds or thousands of records — which is precisely the condition `PRODUCT_ROADMAP.md` recommends testing for next.

TD-29 remains a different flavor of infrastructure debt: hardcoded project-root-relative paths are fine for a hand-run vault, but a blocking issue the moment this needs to be packaged as something a second user could install onto a different machine. Flagged here because it's easy to miss — it reads as "not urgent" from an engineering-debt lens but is load-bearing for the Distribution track in `PRODUCT_ROADMAP.md`. **TD-30 (the sibling item — no settings surface for `destination_root`) is now closed**, resolved by H5 — see "Closed items" below.

### Configuration-experience findings (added 2026-07-23, from H5's Product Acceptance Test)

**TD-41 — EOF-during-prompt uses raw, technical error framing.** Severity recorded as Recommended, not Medium, consistent with this register's convention of not carrying Medium-severity code defects forward (§ header) — this is a diagnostic-quality gap, not an incorrect behavior; no file is ever corrupted or partially written regardless of which abort mechanism is used. `_prompt_path()`'s retry loop has no `EOFError` handling of its own; closing stdin mid-prompt (Ctrl-D, or a scripted/non-interactive invocation that runs out of input) propagates all the way to `main()`'s generic Layer 3 handler, producing `"Unexpected error: EOF when reading a line"` and exit 1 — the identical framing a genuine internal bug would produce. Found via H5-PAT-3 during Product Validation, using a real pseudo-terminal to compare against genuine `SIGINT` (Ctrl-C) at the same prompt, which C1's pre-existing generic handler already handles cleanly (`"Aborted. Run 'status'..."`, exit 3). Not a safety issue — no partial or corrupted write results either way — but a real, evidenced inconsistency between two ways of expressing "stop this wizard."

**TD-42 — `destination_root` used as a raw config-key label in `init`.** `_cmd_init()`'s two `_init_one_setting()` call sites pass `"Downloads source path"` (plain English) for the first setting and the literal string `"destination_root"` (the internal config key) for the second — confirmed by direct read of the call sites. Found via Scenario 1/5 of H5's Product Acceptance Test. A wizard built specifically to be usable without documentation should not lean on internal vocabulary for half its own prompts.

**TD-43 / TD-44 — Unicode escaping in the raw file; no inline format hints in prompts.** Both Low, both cosmetic/polish rather than functional: PyYAML's default `allow_unicode=False` means a unicode/emoji path value round-trips correctly but is stored as escaped codepoints, not literal characters, if a maintainer opens `sources.yaml` directly; neither `init` prompt hints that `~` and relative paths are accepted (both confirmed working) or shows a worked example. Found during Scenarios 3 and 5 of the same PAT.

### C2 first-live-run findings (added 2026-07-23, from the first real run against the live installation)

**TD-45 — `scan()` has no incremental persistence at real scale.** `main.py`'s `scan()` calls `scan_source()` once; that single call does not return until it has finished walking the *entire* configured source directory internally. Only after it returns does `scan()` loop over the results and call `save_file_record()` for each one. `scan_source()` itself writes to `Runtime/Logs/action_log.jsonl` incrementally, per file, as it iterates — so a real, in-progress scan is visible there — but nothing is written to `Database/Metadata/metadata_store.json` until the entire walk completes and control returns to `scan()`.

**Found:** during C2's first live run, against the real, live `~/Downloads` folder (1,107 top-level entries — no prior test, real or synthetic, had exceeded ~45 files). The scan was processing roughly 2 files/second; at that rate the full folder would take on the order of 9–10 minutes. The validation session's own execution environment could not sustain a single command that long, and the scan was interrupted after 85 files (68 discovered, 17 skipped). Every one of those 85 files has a real `discover`/`skip` entry in the action log — but `metadata_store.json` was still exactly `[]` afterward, because the interruption happened before `scan()` ever reached its save loop.

**Impact:** no data was corrupted and no real file was touched — `scan()` never writes to the source folder, only stats/hashes it — and re-running `scan()` from this state is safe (the metadata store was never partially written, so there's nothing to reconcile against). The real cost is wasted work and a confusing log: any real-world interruption of a large scan (not just this session's tooling limit — a closed terminal, a sleeping laptop, a killed process, or a future Scheduled-mode run hitting an unrelated fault) throws away 100% of that scan's progress, while leaving the action log looking like real work happened. A future reconciliation pass reading the action log alone would see "discovered" entries with no corresponding metadata record and have no way to tell whether that file was actually filed, is still pending, or was simply lost to an interrupted scan.

**Recommended fix (not implemented — recommendation only, per this project's design/implementation separation):** incremental checkpointing — call `save_file_record()` for each record as `scan_source()` discovers it (or in small batches), rather than buffering the entire result in memory and saving only at the very end. This would let an interrupted scan retain everything found up to the interruption point, and would let a subsequent scan skip or reconcile against what's already saved instead of starting over. Related to, but more serious than, the already-known TD-03/TD-04 debt ("read-modify-write cost at scale") — this is not just a performance concern, it's all-or-nothing durability, newly surfaced because this is the first time the pipeline has run against real, at-scale content.

### Closed items

Closed 2026-07-23.** Real-world validation (`PATTERN_TRACKER.md` PT-002, Confirmed Pattern across Runs 002/003) confirmed this disclosed risk was broader and more consequential than this register's original "Low, revisit if reported in practice" framing assumed — it affected 27 of 27 real image-family files across both validation datasets, not an edge case. Designed (`Build-out/02 Classification/Module 02 Post-Freeze Design Correction — PT-002.md`), implemented (`src/pipeline/classification.py`), regression-tested (720/720), and re-validated against the original real-world datasets (`PT002_VALIDATION_REPORT.md`, PASS) under `Governance/FROZEN_MODULE_CHANGE_POLICY.md`'s post-freeze change process. **Explicitly not closed by this fix** — kept open here rather than folded into TD-16's closure, since it is a distinct, broader gap TD-16's fix was never scoped to address: image-family files (`.jpg`/`.png`/etc.) still have no route to `Category.Document` even when their true content is a scanned document (only Screenshot/Image are reachable from that extension family) — visible in Run 002's 9 files, which now correctly avoid `Screenshot` but land on `Image`, not `Document`. ## What this register deliberately does not contain

No Critical, High, or unresolved Medium finding exists anywhere in this register — every one found during eight modules' worth of independent audits was fixed before its module's release, per the project's own non-negotiable gate. This register is a list of accepted trade-offs and disclosed gaps, not a defect backlog. That distinction matters for how the roadmap documents that follow should be read: the engine does not need to be fixed before product work begins. It needs to be *used*.
