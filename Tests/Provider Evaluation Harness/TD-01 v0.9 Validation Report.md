# TD-01 v0.9 Validation Report

**Scope:** Implementation validation for TD-01 v0.9 — Provider Registry, Claude API provider, configuration support, opt-in consent flow, and Provider Evaluation Harness. Per `Build-out/02 Classification/TD-01 Provider Architecture — Design Package.md` §7 ("Implementation addendum"), this report checks the implementation against that section's five numbered acceptance criteria and discloses everything this validation cycle could and could not exercise in this environment.

**Governing instruction:** "Proceed with implementation of TD-01 exactly as specified in the revised design package... Stop after implementation and the full validation cycle before proposing any v1.0 work." This report is that stop point.

## 1. What was built (v0.9 scope, as approved)

- `src/providers/registry.py` — two independent, string-keyed provider registries (classification, extraction), zero coupling to `classification.py`/`metadata.py`'s concrete types.
- `src/providers/claude.py` — real, non-interactive `ClassificationProvider`/`MetadataExtractionProvider` implementations calling the Claude API (`anthropic` SDK), registered under `"claude"` as an import-time side effect.
- `src/config/sources.yaml` — three additive keys: `classification_provider`, `extraction_provider`, `ai_provider_consent` (default `false`).
- `src/cli.py` — `provider enable/disable/status` subcommands with explicit disclosure and confirmation.
- `src/main.py` — `_resolve_provider_for_classification()`/`_resolve_provider_for_extraction()`, wired into `classify()`/`extract()`'s existing `provider=None` default path.
- `Tests/Provider Evaluation Harness/` — `run_harness.py`, `fixtures/` (6 files), `expected_answers.json`, `test_run_harness.py`.

Nothing outside this list was implemented — no OpenAI, Gemini, Ollama, or hybrid provider, per the governing instruction's explicit exclusion.

## 2. Acceptance criteria (design §7) — checked against real evidence

**(1) Full regression suite passes at 100% before and after.** `pytest src/` (the project's own established regression suite, per `src/README.md`): **889 passed, 0 failed** — 871 pre-existing tests plus 18 new tests in this same run (`src/providers/test_registry.py`, `src/providers/test_claude.py`, and additions to `src/test_cli.py`/`src/test_main.py`). The harness's own test file, `Tests/Provider Evaluation Harness/test_run_harness.py` (18 tests, not part of `pytest src/` by this project's own colocation convention — it lives under `Tests/`, not `src/`, and tests a `Tests/`-resident tool), also passes at 100% when run explicitly. Combined: **889/889 in `src/`, 18/18 in the harness's own test file, zero failures.**

**(2) `classify()`/`extract()` with no provider configured behaves identically to today.** Verified directly: `_resolve_provider_for_classification()`/`_resolve_provider_for_extraction()` return `None` whenever `ai_provider_consent` is false (the shipped default) or a key is unset — and never themselves construct `ClaudeLiveClassifier()`/`ClaudeLiveExtractor()`; that responsibility remains solely `classify_batch()`/`extract_metadata_batch()`'s own pre-existing default argument. Confirmed with dedicated unit tests (`test_resolve_provider_for_classification_never_constructs_claude_live_classifier` and its extraction counterpart) and an integration-level test that a real `classify()`/`extract()` call routes the resolver's result straight into the batch function unchanged.

**(3) `provider enable` requires confirmation and disclosure, refuses on missing registry key or missing `ANTHROPIC_API_KEY`.** Verified with real CLI invocations (not just unit tests in isolation): `provider enable` prints the full disclosure text (cost, what gets sent, that the key is never persisted) before prompting; refuses cleanly with no config change when `"claude"` isn't registered; refuses cleanly with no config change when `ANTHROPIC_API_KEY` is unset; and a declined (`n`) confirmation leaves `ai_provider_consent: false`. All four paths covered by `src/test_cli.py`'s new provider tests, run against a byte-for-byte realistic sandboxed `sources.yaml`.

**(4) Registry supports exactly one v0.9 entry (`"claude"`) without requiring `main.py`/`ClassificationEngine`/`MetadataExtractionEngine` changes to add a second later.** Verified structurally, not just by inspection: `test_registry_module_has_no_import_of_classification_or_metadata_modules` mechanically checks `registry.py`'s own module globals contain no binding to either engine module. Adding a second provider (e.g. a future `src/providers/openai.py`) would need only its own module plus one more `import` line in `main.py` — no change to the registry, the engines, or the CLI's provider commands (which read the registry's `registered_*_providers()` accessors, not a hardcoded list).

**(5) The harness runs end-to-end against a stub provider and produces all six required metrics.** Verified with a perfect-oracle fake provider registered under a temporary `"test-stub"` key (`Tests/Provider Evaluation Harness/test_run_harness.py`): a full `run_provider("test-stub")` call produces `accuracy`, `unknown_rate`, `naming_quality`, `tier_counts`, `mean_latency_ms`, and `estimated_cost_usd` — all six, all internally consistent (tier counts sum to the fixture count; cost is `None`, not a silently-wrong `$0.00`, when the fake's model has no pricing-table entry). Separately, the harness was also run end-to-end against the **real** `"claude"` provider (see §3 below) — a materially different, higher-value validation than the stub run alone, since it exercises the actual production code path.

All five acceptance criteria: **met**, with evidence above, not just checked off.

## 3. Harness dry run against the real `"claude"` provider

Executed `python3 "Tests/Provider Evaluation Harness/run_harness.py" -y` in this environment (no `ANTHROPIC_API_KEY` set — see §4 for why). Full output:

```
About to benchmark: ['claude']
Fixtures: 6 (in .../Tests/Provider Evaluation Harness/fixtures)

provider      accuracy  unknown%   naming%  auto  appr   rev   lat(ms)     est.$
--------------------------------------------------------------------------------
claude           66.7%     33.3%     66.7%     2     0     4       n/a       n/a

claude — per-file fallbacks:
  - <4 fixture file_ids>: provider_exception — ProviderUnavailableError: ANTHROPIC_API_KEY is not set...
```

This is the harness correctly exercising the real, shipped **unconfigured-provider fallback path** end-to-end: 4 of 6 fixtures needed a live judgment call and got none, so they fell back to `Category.UNKNOWN`/null fields exactly as designed (not a crash, not a silent wrong answer) — 100% of the two genuinely judgment-dependent fixtures correctly logged a named, actionable `fallback_reason`. The other 2/6 (66.7% accuracy) resolved correctly because they're either deterministic-by-extension (`archive.zip`, `MyApp_1.2.3_Mac.dmg`) or a fixture where "Unknown" is itself the correct answer (`ambiguous_note.txt`) — none of these three ever call a provider, so the missing key doesn't affect them. This result is a real, faithful demonstration of the fallback contract working correctly under exactly the "opted in but no key" condition — not a representative measure of Claude's classification accuracy (see §4).

## 4. Disclosed gap: no live API validation in this environment

**No `ANTHROPIC_API_KEY` is set in this sandbox environment** (`env | grep -i anthropic` returns nothing). This means: no test in this validation cycle made a real network call to the Claude API, and the harness dry run above exercised only the *unavailable-provider* fallback path, not a real classification/extraction judgment call.

**Network egress to Anthropic's API is confirmed working**, though: `curl -sS -m 8 https://api.anthropic.com/v1/models` returns `HTTP 401` (an authentication rejection, not a connection failure or timeout) — meaning if a real key is supplied, this environment can reach the API and a live run would exercise the actual code path, not just the error-handling branch.

Consistent with this project's established disclosure discipline (`CHANGELOG.md`'s BUG-001 precedent — "state verification scope precisely, never gloss over what wasn't tested"): **this validation cycle proves the architecture, wiring, consent flow, fallback behavior, and harness mechanics are all correct — it does not prove Claude actually produces good classifications/extractions on real files**, because no real judgment call was ever made. That specific question (does the Claude API's real output improve Unknown %/naming quality/confidence distribution the way the design's problem statement projects) requires a user-supplied `ANTHROPIC_API_KEY` and a real harness run — recommended as the first action before broader use, not before this stop point.
