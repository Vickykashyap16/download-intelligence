# H5 Completion Report — Configuration Experience

**Status:** CLOSED, 2026-07-23 · **Date:** 2026-07-23 · **Scope:** H5 only (`PRODUCT_READINESS_REVIEW.md` High finding H5; selected as the highest-priority remaining v0.9 item per C1's own Findings Classification & Release Planning Matrix, U5)

---

## Objectives achieved

Deliver a real, guided settings surface so a user can point the pipeline at a real Downloads folder and destination without hand-editing `src/config/sources.yaml` — replacing the prior state, where the only way to configure a source path or `destination_root` was to open the YAML file directly, with no validation and no protection against silent corruption of hand-typed special characters. That objective is met: `python -m src.cli init` (a guided, first-time/reconfigure wizard) and `config --set-source`/`--set-destination` (single-value updates) both exist, validate input before writing, and preserve every comment and unrelated line in the file. The Product Acceptance Test independently confirmed, via fresh repro rather than restated claims, that this resolves C1-PAT-1 (the "Unexpected error"-framed unconfigured-scan crash), TD-30 (no settings surface of any kind), and the first-run onboarding gap — the same three problems the PAT was explicitly asked to verify against.

## Scope delivered

`src/cli.py`: `init` (interactive wizard for the Downloads source path and `destination_root`, validates each as an existing directory, shows and confirms before replacing an already-set value) and two new flags on the existing `config` subparser, `--set-source`/`--set-destination` (single-value, non-interactive updates, same validation). Both route through a new targeted, comment-preserving line-replacement writer (`_write_config_value()`) rather than a full YAML round-trip or a new dependency — chosen specifically to avoid `ruamel.yaml` while `PRODUCT_READINESS_REVIEW.md` finding H1 (a broken, double-pinned `requirements.txt`) remains open. `scan`/`run` gained a narrower exception-handling wrapper distinguishing "not configured" (friendly message, exit 0) from "configured but the path no longer exists on disk" (a second, previously-unnamed gap found during this work package's own Repository Impact Analysis) from genuine internal errors (uncaught, Layer 3, exit 1) — a three-way diagnostic classification now recorded permanently as `Governance/ARCHITECTURE_DECISIONS.md` decision 33. Full lifecycle: Design Package → Engineering Review (F1–F6) → Implementation (WP-1–WP-7) → Implementation Audit → Implementation Report, then Product Validation: PAT Plan (6 scenarios, executed for real in an isolated sandbox) → Product Acceptance Report. All in `Build-out/09 CLI & Product Interface/` and `Tests/`.

## Remaining known issues

Full detail: `TECHNICAL_DEBT_REGISTER.md` (TD-41 through TD-44, all Recommended/Low).

- **TD-41 (Recommended):** closing stdin mid-prompt (EOF — Ctrl-D, or a scripted invocation that runs out of input) during `init` surfaces a raw `"Unexpected error: EOF when reading a line"`, exit 1 — the same alarming framing this work package was built to move away from for the "not configured" case. A genuine `SIGINT` (Ctrl-C) at the same prompt is already handled cleanly by C1's pre-existing generic handler. Not a safety issue — no partial or corrupted write results either way.
- **TD-42 (Recommended):** the `init` wizard's second prompt uses the raw internal config key `destination_root` as its label, inconsistent with the first prompt's plain-English "Downloads source path."
- **TD-43 (Low):** unicode/emoji path values are stored as escaped codepoints rather than literal characters in the raw YAML file — valid and lossless, but not human-legible if a maintainer opens the file directly.
- **TD-44 (Low/Enhancement):** neither `init` prompt gives an inline example or format hint (e.g. that `~` and relative paths are both accepted — confirmed working).
- **Disclosed, not scored:** permission-denied source paths could not be freshly, independently re-exercised during this PAT — the sandbox's mount rejected the `chmod`/`rm` operations needed to construct the case. Covered only by the project's existing automated unit tests, not by this validation round.
- **Inherited from the Implementation Report, unchanged:** `_write_config_value()` is a targeted, two-key writer, not a general YAML editor (deliberate, per the accepted design); `init` has no non-interactive/scriptable mode; the one inline comment on `sources.yaml`'s `path:` line is dropped, not preserved, the first time a real value is written (deliberate, disclosed); `src/pipeline/watch_ingest.py`'s independent `_SOURCES_CONFIG_PATH` copy remains a documented, non-drift-risk triplication, not fixed here (out of scope).

## Lessons learned

Adversarial, realistic-length testing caught a real defect the design's own stated verification method hadn't anticipated: the first working value-serializer had no explicit `width` argument, so PyYAML's default 80-column wrap silently corrupted long (realistic `tmp_path`-length, not short hand-picked) values — found, root-caused, and fixed (`width=float("inf")`) before implementation was considered complete, and independently re-confirmed with even more adversarial inputs (full paths with `#`/`:`/quotes/spaces/unicode together) during this PAT with zero further corruption. Testing the real, unmocked `load_source_config()`/`scan_source()` path rather than only mocking `run_scan()` surfaced a genuine, previously-undisclosed three-way constant duplication (`watch_ingest.py`'s own `_SOURCES_CONFIG_PATH`) that a narrower test would have missed entirely. Using a real pseudo-terminal (Python's `pty` module) to deliver a genuine `SIGINT`, rather than only piping stdin, was necessary to distinguish a real recovery gap (EOF framing, TD-41) from a testing-method artifact (the piped-transcript prompt/confirmation run-together observed in Scenario 1, traced to the absence of terminal echo in a non-interactive capture, not a real wording defect) — a distinction that would have been missed, or wrongly logged as a defect, without the extra rigor.
