## Design/review conformance

- **F2 (Mandatory — severity classification defined and consistently applied) — confirmed.** `Governance/ARCHITECTURE_DECISIONS.md` decision 33 classifies H5 as High (same tier as C1, decision 32) and states the three-way diagnostic classification (expected precondition → exit 0; re-promptable input → no exit; genuine write failure → raises, reaches Layer 3 → exit 1) by name. Verified against the actual code, not just the decision text: `_run_scan_with_friendly_config_errors()` returns 0 for both caught exception types; `_prompt_path()`/`_confirm()` never `return`/`raise` on bad input, only re-prompt; `_write_config_value()`'s every raise path (line not found, write failure, verification mismatch) is uncaught anywhere between it and `main()`'s own Layer 3 `except Exception` — confirmed by grep, no `try/except` around any `_write_config_value()` call site in `_cmd_init`/`_cmd_config`.
- **F3 (absolute path resolution) — confirmed.** `_resolve_existing_directory()` is the single path-validation function used by both `_prompt_path()` (interactive) and `_cmd_config`'s `--set-source`/`--set-destination` handling (non-interactive); it always returns `Path(raw).expanduser().resolve()` or `None`, never the raw string. Every call site (`_init_one_setting`, `_cmd_config`) passes `str(resolved)` — the resolved, absolute path — to `_write_config_value()`. Confirmed by direct read: no code path writes `raw`/`set_source`/`set_destination` (the unresolved argument strings) directly.
- **F4 (precise line matching) — confirmed.** `_find_source_path_line()` requires the `path:` line's indentation to be strictly deeper than `- source_id: downloads`'s own indentation and stops scanning (raising) at the first line that dedents back to or past that level. `_find_destination_root_line()`'s regex (`^destination_root:\s*.*$`) has no leading `\s*`, so it cannot match an indented/nested line. Both are exercised directly (not only through the higher-level `_cmd_init`/`config` commands) by `test_find_source_path_line_stops_at_end_of_source_block` and `test_find_destination_root_line_ignores_nested_key_of_the_same_name`.
- **F5 (`config set` argparse shape decided) — confirmed.** Implemented as `--set-source`/`--set-destination` flags on the existing `config` subparser (the Engineering Review's own recommended option), not a nested sub-subparser — `build_parser()` adds no second-level `add_subparsers()` call anywhere. `test_parser_config_set_options` confirms both flags parse correctly together and default to `None` when absent.
- **F6 (exit-code caveat carried forward) — confirmed.** `_run_scan_with_friendly_config_errors()`'s own docstring states the inherited, still-open C1 §3.5 question (exit 0 may be unsatisfying for a future scripted/scheduled caller) explicitly, rather than presenting H5's exit-0 choice as newly and independently settled. Decision 33's "Trade-offs" section states the same thing as the permanent record.

## Finding — identified and corrected during implementation, before this was considered complete

**`yaml.safe_dump()`'s default line-wrapping silently corrupted long values — caught by a realistic test, not a short hand-picked one.** The first working version of `_yaml_safe_scalar()` called `yaml.safe_dump(value, default_flow_style=True)` with no `width` argument. PyYAML's default wrap width is 80 columns; a value longer than that (a fully-qualified, deeply-nested path — exactly the realistic case a real installation would produce, not an edge case) gets broken across two physical lines by the dumper. `_yaml_safe_scalar()`'s own "first line only" extraction then returned a truncated, unterminated quoted scalar, and the very write-then-verify safety net F1 requires caught the resulting corruption immediately (`test_write_config_value_handles_yaml_special_characters` failed with a YAML parse error, not a silent pass) — but the underlying defect was real: a length-triggered variant of exactly the class of bug F1 exists to prevent, distinct from the character-content-triggered case the finding was originally written against.

**How it was found:** a short, hand-typed example value during initial manual verification (`/tmp/x/Archive #2: Client's "Files"`, well under 80 characters) round-tripped correctly and gave false confidence; the committed test instead uses `tmp_path`-prefixed values (pytest's real fixture paths, ~130+ characters in this sandbox) specifically because they're realistic, not because they were expected to fail — the failure was discovered by running the test, not anticipated in advance.

**Severity:** the same class of risk F1 itself is Medium for — contained by the write-then-verify/revert safety net (no corrupted file is ever left in place; the user gets a precise, actionable failure message either way), but a real defect in the "safely support" half of F1's requirement, not just the "or fail precisely" half.

**Fix applied:** `yaml.safe_dump(value, default_flow_style=True, width=float("inf"))` — disables line-wrapping entirely, so the scalar is always emitted on exactly one line regardless of length. `_yaml_safe_scalar()`'s docstring documents why `width` is set explicitly and what breaks without it. No other change was needed; the write-then-verify mechanism itself required no correction, since it did exactly what it was designed to do (refuse to accept a corrupted write) — it just should never have needed to fire for this input in the first place.

## Confirmed non-issues (checked, not overlooked)

- **`src/pipeline/watch_ingest.py` independently re-derives its own copy of `_SOURCES_CONFIG_PATH`** (a third copy, alongside `main.py`'s and `cli.py`'s own — the two-file case `cli.py`'s own module comment already discusses). Not a production defect — all three copies compute the identical value and there is no drift risk in three files independently expressing "this file's own directory (or the project root) + `src/config/sources.yaml`" the same way, exactly the reasoning `cli.py`'s existing comment already gives for the two-file case. It did, however, require this work package's own tests (the first ones in this project to call real `scan()` → real `load_source_config()` end-to-end rather than mocking `run_scan()`) to patch all three module-level constants, not two — `_write_realistic_sources_config()` does this and documents why. Not fixed in production code: out of scope for H5 (NG2 explicitly excludes injectable base paths, TD-29), and renaming or consolidating three already-correct, already-independently-tested constants is not a configuration-experience change.
- **`_cmd_init` raising all the way through to `main()`'s Layer 3 on a genuine write failure is not exercised by an end-to-end test through `_cmd_init` itself** — only its two constituent pieces are (`_write_config_value()`'s own revert-on-failure test; `main()`'s generic Layer 3 handling, tested since C1). Assessed as low risk: `_init_one_setting()` adds no logic between the two beyond a direct call, and no `try/except` of any kind sits between them (confirmed by reading `_cmd_init`/`_init_one_setting` in full) — an integration test here would verify composition, not new logic, matching the same reasoning `preview()`/`execute()` fresh-reload behavior was already checked-not-retested in C1's own audit (finding F5 there).
