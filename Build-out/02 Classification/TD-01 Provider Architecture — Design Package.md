# TD-01 Provider Architecture — Design Package

**Status:** Design only — nothing in this document has been implemented.
**Scope:** Resolves `TECHNICAL_DEBT_REGISTER.md` TD-01 ("No autonomous production Classification/Metadata Extraction provider," target `v0.9.0+ decision`, affects Modules 02 and 03).
**Framing:** TD-01 as a product architecture problem — which intelligence backend should power `ClassificationProvider`/`MetadataExtractionProvider` when no human is present, not how to code it.
**Revision note (this pass):** approved with one architectural refinement — v0.9 introduces a provider framework with a configurable provider registry rather than a single hardcoded backend, and this revision adds a Provider Evaluation Harness design so future registry entries can be benchmarked against the same validation dataset before being recommended for default use. Claude remains the only concrete implementation shipped in v0.9. Sections 1–4 are the original comparative analysis (unchanged); Sections 5–6 are new.

## 1. The problem, restated as architecture

Both Module 02 (`ClassificationProvider`) and Module 03 (`MetadataExtractionProvider`) were designed with a frozen abstract provider boundary specifically so a real backend could be swapped in later without touching the engine, batch orchestration, storage, or confidence layers (`Module 02 Design.md §25`). Today the only concrete implementation of either (`ClaudeLiveClassifier`/`ClaudeLiveExtractor`) is a documented placeholder that only "executes" inside a live, human-driven Claude conversation. Every judgment-dependent file run outside that context falls back to `Category.UNKNOWN` / null extraction fields.

The C2 Sandbox Product Validation Report and Retrospective quantified the real-world cost of this, both on an 8-file sandbox set and on the real 866-file production Downloads folder:

- Unknown %: 37.5% (sandbox) / 37.1% (real) — consistent across both.
- Naming fallback rate: 37.5% (sandbox, 3/8) / 52.9% (real).
- Fully-complete extraction (of eligible files): 60% (sandbox) / 10.3% (real).
- `review_required` %: 75% (sandbox) / 89.1% (real).
- `approval_required` %: 0% (sandbox) / 0.8% (real) — the middle tier is nearly unused, largely because files either resolve cleanly (deterministic, ~100) or fall to `Category.UNKNOWN`'s hard floor / accumulate enough naming-fallback penalty to drop well under 80 in one step.

This is the single largest lever identified in the Retrospective (accounted for the largest deduction in the 56% product-readiness estimate). The question this document answers: **what should actually answer the judgment call when no human is present** — not whether to build it.

## 2. Candidate architectures

Seven candidates, evaluated against the frozen `ClassificationRequest`/`ClassificationResult` and `MetadataExtractionRequest` contracts (both already provider-agnostic by design — no candidate below requires a contract change, only a new concrete class).

1. **Claude API** — Anthropic's hosted API, text + vision, called autonomously (network call, not a live chat session).
2. **OpenAI API** — GPT-4o/4.1-class hosted API, text + vision.
3. **Gemini API** — Google's hosted API, text + vision.
4. **Ollama (local LLM)** — a locally-run open-weight model (e.g., Llama 3.2 Vision, Qwen2-VL) via a local inference server, no network call.
5. **Hybrid (tiered)** — deterministic Pass 1 (already exists, unchanged) → local OCR/rules pre-pass → cloud LLM call only for the residual ambiguous minority.
6. **Local vision/OCR + rules only** — Tesseract-class OCR plus expanded keyword/pattern rules, no generative model at all.
7. **Rule-based fallbacks only** — expand today's deterministic Pass 1 (more extensions, filename heuristics), no OCR, no vision, no LLM.

## 3. Decision matrix

Ratings are relative to each other, not absolute. For Cost/Latency, **Low is good** (cheap/fast). For every other column, **High is good**.

|---|---|---|---|---|---|---|---|---|
| Claude API | Low–Med | Med | Low | None | High | High | High | High |
| OpenAI API | Low–Med | Med | Low | None | Med | High | High | High |
| Gemini API | Low | Low–Med | Low | None | Med | Med–High | Med–High | Med–High |
| Ollama (local LLM) | None (compute only) | Med–High | High | Full | Low–Med | Med | Med | Med |
| Hybrid (tiered) | Low | Low–Med | Med–High | Partial | Low | High | High | High |

### Rationale by candidate

**Claude API.** Reuses the exact `ClassificationRequest`/`ClassificationResult`/`MetadataExtractionRequest` contracts already frozen — this is a new concrete provider class, not a new architecture. Quality has a real track record on *this specific dataset*: PT-002 and PT-003's corrections, and every UAT/PAT judgment call across Modules 02–07, were made by live Claude judgment. Cost at this product's actual scale (a personal Downloads folder, a few hundred judgment calls per run, run occasionally not continuously) is small in absolute terms, but not zero, and it's metered spend for what has been a fully local, free-to-run tool until now. Privacy is the real cost: file content — including, confirmed in this validation, financial screenshots, a Companies Act legal filing, and files literally named `TTTadmin_codecommit_credentials.csv` and `hpkekeyconfig` elsewhere in the sample folder — would leave the machine. No offline mode. Maintainability is high specifically because it's the smallest possible change: one new class, no new subsystem.

**OpenAI API.** Architecturally identical position to Claude (same ABC, same "just a new class" cost), and Gemini/GPT-class models are competitive on raw multimodal quality. The real cost is organizational, not technical: this product's entire design language, prompting conventions, and quality evidence (PT-002, PT-003, every UAT) are built around Claude's judgment specifically. Adding a second AI vendor means a second prompt-tuning effort from zero evidence, a second API key/credential to secure, a second failure/rate-limit mode to handle — for a quality outcome that's likely comparable, not better. Same privacy exposure as Claude, with no offsetting benefit.

**Gemini API.** Same privacy/offline profile as the other two hosted APIs, with a genuine cost/latency edge (Flash-tier pricing and speed are usually the best of the three). Rated slightly below Claude/OpenAI on expected impact only because, like OpenAI, there's no existing evidence base on this product's actual data — the rating reflects that gap, not a belief that Gemini is categorically worse at the task.

**Ollama (local LLM).** The strongest privacy/offline story of any generative option — nothing leaves the machine, no metered cost. But it shifts real cost onto the user: install and run a local inference server, pull a multimodal model (several GB), and have enough RAM/VRAM to run it acceptably. This is a materially heavier ask than anything this product has required so far (H5's own PAT work found even a guided `init` wizard needed real UX care) — a bare `ollama pull` step is not equivalent to that. Local vision-model judgment quality on nuanced document-type distinctions (Invoice vs. Contract vs. generic Document) is generally behind frontier hosted models today, so the Unknown %/naming/confidence impact, while real, is smaller and less predictable than a hosted frontier model's.

**Hybrid (tiered).** Keeps the existing deterministic Pass 1 untouched, adds a cheap local pre-pass (OCR + keyword rules) that can resolve some of the easier ambiguous cases without any AI call at all, and reserves a cloud LLM call for the genuine residual minority. This directly mirrors the product's own existing design philosophy — deterministic-first, judgment only where deterministic signals run out (exactly how `ClassificationEngine.classify_file()` is already structured) — extended one layer further rather than replaced. Cost/latency/privacy exposure are all bounded to just the subset of files that actually need it (today, that's the ~37% landing on Unknown, not all files), which is the best ratio of any candidate on this list. The cost is engineering complexity: two provider implementations plus routing logic, and a real, new consent question (when does a file get sent to the cloud, and does the user get asked) that doesn't exist for a single-backend design.

**Local OCR + rules only.** A legitimate, low-risk complement to any of the above (it's what Hybrid's pre-pass *is*), but not a standalone answer to TD-01. OCR text plus keyword rules can plausibly catch some strongly-signaled cases (a PDF containing "INVOICE" or "Companies Act" in its first page), but Module 03's `description`/`variant` extraction fields are free-text summarization, not keyword extraction — no rule set produces those. This closes part of the classification gap and essentially none of the extraction gap.

**Rule-based fallbacks only.** Not a real candidate for the deep-pass gap — Module 02 was explicitly designed as hybrid (deterministic + judgment) specifically because extension/filename alone was already proven insufficient for text-bearing/image content before any of this validation happened. Included here for completeness, not as a viable resolution.

## 4. Recommendation

### v0.9: a provider framework with a configurable registry — Claude the only implementation, not an assumed permanent one

Revised from the original recommendation ("implement one Claude class") to: introduce a **provider registry** as the actual v0.9 deliverable, with a Claude-backed `ClassificationProvider`/`MetadataExtractionProvider` pair as the registry's only registered entry. The distinction matters architecturally even though the user-visible behavior of v0.9 is identical either way (Claude, opt-in, off by default): today's `classify(provider=None)`/`extract(provider=None)` default falls back to a *hardcoded* reference to `ClaudeLiveClassifier`/`ClaudeLiveExtractor` — a name baked into `main.py`'s call sites. A registry replaces that hardcoded reference with a lookup by configured key, so the day OpenAI, Gemini, Ollama, or a hybrid tier (§2) is actually built, it's a new registration, not a rewrite of every call site that currently assumes Claude.

This directly answers the OpenAI/Gemini rationale's own stated cost in §3 ("a second prompt-tuning effort from zero evidence... for a v0.9 that isn't asking that question yet") — the registry doesn't pre-build a second provider, it just makes sure v0.9's one real implementation doesn't quietly become a second hardcoded assumption the way `ClaudeLiveClassifier` already is today.

Still recommended over OpenAI/Gemini/Ollama/hybrid as the *implemented* v0.9 backend for the same reasons as the original recommendation: only Claude has an existing quality track record on this product's real data (PT-002, PT-003, every UAT judgment call), and v0.9 should prove the product concept (does resolving TD-01 actually deliver the auto/review shift the Retrospective predicts) before investing in evaluating or building alternatives.

### v1.0: hybrid, local-first, cloud-optional — populated into the same registry

Unchanged in substance from the original recommendation: by v1.0 (general-consumer-facing, per `PRODUCT_ROADMAP.md`), move to a tiered architecture — deterministic Pass 1 unchanged, a local OCR/keyword pre-pass ahead of any AI call, cloud calls reserved for the residual ambiguous minority, and a genuine fully-offline mode as a first-class option. The refinement changes *how* this arrives: each tier's backend (a local OCR/rules provider, a cloud provider, an Ollama provider) is a new registry entry, evaluated via the harness in §6 before being wired in as v1.0's default, rather than a bespoke new subsystem built on faith.

## 5. Provider registry architecture (v0.9)

**What it is.** A small, explicit mapping from a configuration key (a plain string, e.g. `"claude"`) to a factory that produces a `ClassificationProvider` or `MetadataExtractionProvider` instance — one registry per provider kind, mirroring the fact that `ClassificationProvider` and `MetadataExtractionProvider` are already separate ABCs (Module 02 §25 / Module 03's equivalent) with no shared base today, and this design doesn't unify them. Deliberately not a plugin-discovery system, dependency-injection framework, or anything that scans the filesystem for providers — every registered provider is still an explicit, reviewed line of code in the project, consistent with this project's existing "no code no one wrote" discipline. The registry's only job is indirection: turning "which provider" from a hardcoded class reference into a looked-up one.

**Where it lives.** A new small module (e.g. `src/providers/registry.py`, exact location an implementation-time detail) owning two dicts — `CLASSIFICATION_PROVIDERS: Dict[str, Callable[[], ClassificationProvider]]` and `EXTRACTION_PROVIDERS: Dict[str, Callable[[], MetadataExtractionProvider]]` — populated at import time by each concrete provider module registering itself (e.g. `classification.py`'s Claude implementation calls `register_classification_provider("claude", ClaudeAPIClassifier)` at module load). v0.9 ships exactly one entry in each dict.

**Configuration.** A new key in `src/config/sources.yaml`, e.g. `classification_provider: claude` / `extraction_provider: claude` (naming allows them to diverge later — Module 03 could reasonably adopt a provider before Module 02 does, or vice versa), read the same way `destination_root` already is (`_load_destination_root()`'s established pattern in `main.py`). Absent or unset resolves to the same "no live judgment, fall back to Unknown" behavior the product has today — the registry changes *how* a provider is selected, not the safe-by-default posture when none is configured.

**Resolution flow.** `classify()`/`extract()` in `main.py` currently accept `provider=None` and fall back to instantiating `ClaudeLiveClassifier()`/`ClaudeLiveExtractor()` directly. Under the registry, a `None` falls back to `resolve_classification_provider(config_key)` instead, which looks up the configured key in the registry and instantiates it — raising a clear, actionable error (not a silent fallback to Unknown) if the configured key isn't registered, mirroring H5's own "expected, not error" vs. "genuine problem" diagnostic discipline. The explicit `provider=` parameter itself is untouched — tests and any future live-session override keep working exactly as they do today (`classify(provider=my_live_provider)`).

**Why this doesn't cost v0.9 anything material.** Every other layer — `ClassificationEngine`, `classify_batch()`'s orchestration, storage, confidence scoring, CLI — already only knows about the `ClassificationProvider`/`MetadataExtractionProvider` ABC, never a concrete class name (§25's frozen boundary is exactly what makes this possible). The registry is new code at the single point those layers currently hardcode a default; it does not touch anything downstream of "a provider instance exists."

## 6. Provider Evaluation Harness (design)

**Purpose.** A standalone benchmarking tool, separate from the production pipeline, that runs every registered provider against the *same* fixed validation dataset and produces directly comparable metrics — so a future registry addition (OpenAI, Gemini, Ollama, a hybrid tier) is recommended for default use on evidence, the same way Claude's own recommendation in §4 rests on PT-002/PT-003/UAT evidence rather than assumption.

**Not a production feature.** Never invoked by `scan`/`run`/`preview`/`execute`, never runs automatically, and never touches real user Database/Runtime state — same isolation discipline already established and used this session for the C2 sandbox validation (an isolated project copy with its own empty Database, real files read-only as input). Running the harness is an explicit, operator-invoked action, since for any cloud provider it means real, metered API spend — the harness must print an estimated-cost figure and require confirmation before calling a paid provider, not just after.

**The validation dataset.** Accuracy requires a ground truth, which the C2 sandbox set doesn't have (this session's evaluation was manual, one file at a time, against my own reading of each file's actual content). The harness needs a small, hand-curated, version-controlled fixture set — a natural extension of `Samples/`/`Tests/` — where each file has a companion expected-answer record: expected `Category` (or explicitly `Unknown`, for fixtures that are genuinely ambiguous even to a human, so a provider correctly landing on Unknown scores as *correct*, not as a miss), and expected values (or "no correct answer exists") for the judgment-dependent extraction fields (`description`, `variant`, `app_name`, etc.). Composition should deliberately include the two concrete gaps this validation already found: a legal/corporate-style document (the INC-34 case) and a renamed, resized screenshot — so the harness measures against known-hard cases, not just easy ones.

**What it measures, per provider, per run:**

- **Accuracy** — % of fixtures where the provider's returned `Category` matches the fixture's expected label (including correctly-Unknown fixtures scoring as correct).
- **Unknown %** — % of fixtures the provider left at `Category.UNKNOWN`, reported separately from accuracy so "appropriately cautious" (correct Unknown) and "actually wrong" (should have resolved, didn't) are never conflated into one number.
- **Naming quality** — % of fixtures where `suggest_naming_and_destination_batch()` produced a suggested name/destination with zero fallback fields (`naming_signals.fields_fell_back` empty), run downstream of the provider under test, since naming quality is a direct function of how complete that provider's extraction was.
- **Confidence distribution** — the resulting `auto`/`approval_required`/`review_required` tier breakdown after running the *full* downstream chain (extract → duplicate detection → naming → confidence scoring) on the provider's classification/extraction output. This is deliberately not a provider-level number — Module 06 is fully deterministic (§2 of this document's own candidate list) — the harness runs it anyway per provider because tier distribution is the real-world outcome this whole design package is trying to move, and it's the clearest side-by-side signal of provider quality a non-technical reviewer could read.
- **Latency** — per-file and total wall-clock time, read from `EngineResult.processing_time_ms` / `ProviderMetadata.latency_ms`, both of which already exist in the frozen contracts (§25) — no new instrumentation needed for this metric.
- **Estimated cost** — requires one addition to `ProviderMetadata` (currently `provider_name`/`model`/`provider_version`/`latency_ms`/`reasoning`): a `token_usage` field (input/output token counts, or the closest equivalent a given vendor's API reports), which the harness then multiplies against a small, harness-owned pricing table (kept in the harness, not in the frozen provider contracts, since pricing changes independently of the architecture). Providers with no metered cost (Ollama, OCR/rules) report `0` — a real, comparable number, not an omitted column.

**Output.** One comparison table, one row per provider under test, the six columns above — a decision-support artifact for a future design-package revision recommending which registry entry becomes the new default, not a pass/fail gate baked into any release process.

## 7. Implementation addendum (pre-implementation, Engineering Change Playbook)

TD-01's register entry classifies it "High-impact gap" — treated as **High severity** for playbook purposes (`ENGINEERING_CHANGE_PLAYBOOK.md` §3), which calls for the full ten-section package plus an independent review round before implementation. Sections 1–6 above cover problem statement, root cause, alternatives (the seven-candidate comparison), and the selected approach; this addendum adds the remaining sections the playbook's template names explicitly, so the Design stage is complete before Implementation begins. The user's approval of §4/§5/§6 (registry + harness refinement) stands as the required project-owner approval gate (`ENGINEERING_CHANGE_PLAYBOOK.md` §2, "Review → Implementation").

**Risk assessment.** Highest risk: sending real user file content (confirmed sensitive — financial screenshots, legal filings, credential-adjacent filenames) to a third-party API without genuine, informed consent. Mitigated by: opt-in required, off by default, explicit disclosure before enabling, API key read from an environment variable never written into tracked config. Second risk: a network/API-key/rate-limit failure degrading the pipeline. Mitigated structurally — `ProviderUnavailableError`/`ProviderError` already exist and already have a defined fallback path (Category.UNKNOWN / null fields), so a Claude API failure degrades to *exactly* today's unconfigured behavior, not a crash. Third risk: registry indirection introducing a new class of "unregistered/misconfigured key" failure mode not present today. Mitigated by: fail clearly (a named, actionable error) rather than silently falling back to Unknown, so a typo in config is visibly a config problem, not a silent quality regression.

**Compatibility analysis.** `ClassificationProvider`/`MetadataExtractionProvider` ABCs, `ClassificationRequest`/`ClassificationResult`/`MetadataExtractionRequest`/`ProviderResponse` dataclasses, and both exception vocabularies are unchanged — the new Claude API provider classes implement the existing abstract methods with the existing request/response shapes. The one disclosed exception, already named in §6: `ProviderMetadata` (independently defined in both `classification.py` and `metadata.py`) gains one new optional field, `token_usage` (input/output token counts, default `None`), needed for the harness's estimated-cost metric — added identically to both files' copies per their existing convention-following-not-sharing pattern (§21 of each module's design). Additive with a default; every existing call site constructing a `ProviderMetadata` without it is unaffected. `ClaudeLiveClassifier`/`ClaudeLiveExtractor` (the interactive-session placeholders) are untouched and remain the default when no provider is configured — the registry is strictly additive. The explicit `provider=` parameter on `classify()`/`extract()` keeps its current meaning and precedence (an explicit argument always wins over config resolution). One new dependency (`anthropic`, the official SDK) is added the same way `numpy` was made explicit after BUG-001 — declared, not silently transitive.

**Regression impact.** Every existing test in `test_classification.py`/`test_metadata.py`/`test_main.py`/`test_cli.py` exercises `ClaudeLiveClassifier`/`ClaudeLiveExtractor` or fake providers passed explicitly — none of them resolve a provider through the registry today, so none should change behavior. The only production call sites touched are `main.py`'s `classify()`/`extract()` default-resolution branch (`provider is None`) and `src/config/sources.yaml`'s schema (additive keys only, existing keys unchanged).

**Test plan.** Unit tests for: the registry (register/resolve/unknown-key error, both dicts independently); the Claude API provider classes with the `anthropic` client mocked (success path for both text and vision modes, every mapped error condition raising the correct `ProviderUnavailableError`/`ProviderError`, response-validation edge cases already covered by the existing `_validate_category()`/`_validate_and_merge()` trust boundary — no new validation logic needed there); the CLI `provider enable/disable/status` flow (scripted-input pattern already established in `test_cli.py`, isolated config file); the harness's mechanics using a fake/stub registered provider (proving the metrics computation and isolation are correct without spending real API calls in the test suite). No test calls the real Anthropic API — consistent with this project's existing convention that automated tests never depend on a live provider.

**Acceptance criteria.** (1) Full regression suite passes at 100% before and after. (2) A `classify()`/`extract()` call with no provider configured behaves identically to today (byte-for-byte same fallback path). (3) `python -m src.cli provider enable` requires explicit confirmation and a real disclosure, and refuses to enable a provider whose registry key doesn't exist or whose required environment variable isn't set. (4) The registry supports exactly one entry per provider kind in v0.9 (`"claude"`) without preventing a second entry from being added later without touching `main.py`/`ClassificationEngine`/`MetadataExtractionEngine`. (5) The harness runs end-to-end against a stub provider and produces all six required metrics.

**Rollback strategy.** Every change is additive (new module, new config keys, new CLI subcommand, one new default-resolution branch). Rollback is: revert the `main.py` default-resolution change (restores the hardcoded `ClaudeLiveClassifier()`/`ClaudeLiveExtractor()` calls), and/or leave `ai_provider_consent: false` (the safe default) — no data migration, no schema downgrade, no effect on `Database/`/`Runtime/` state, since this feature never touches either differently than today's placeholder path does on failure.

## 8. What this document does not decide

Left open for future, separate design work: exact prompt design for the Claude provider; how per-run cost is estimated and shown to the user in the *production* opt-in flow (distinct from the harness's own cost-confirmation step above); whether opt-in is a one-time setting or a per-run confirmation; retry/secondary-provider behavior (TD-31, explicitly deferred alongside TD-01 already); the hybrid tier's routing threshold (what "ambiguous enough to escalate to cloud" means, precisely) for v1.0; the exact composition/size of the Provider Evaluation Harness's validation dataset beyond the two known-hard cases named above; and the exact registry module location/API surface (`src/providers/registry.py` above is illustrative, not committed). No code has been written or changed as part of this document.
